# v0.1.1 storage & retained history: design

23 November 2026 · Phase 5 of `docs/v0.1.1-plan.md` (slice 9). Status: **agreed 23 November 2026**: local SQLite is the default and works alone; retained history is optional, in Garage (in-house, next to quiet) or a bucket the owner brings (R2, S3, S3-compatible). The decisions at the end stand unless changed before 5a merges. Screens: Paper "quiet · v1.1 storage & retention", boards 01–29 (matched once Paper is open; this doc fixes the behaviour they draw).

## Goal

Keep searchable history longer than the local disk allows, in object storage the owner controls, without a second database to run. The local window (today: SQLite, 1h–7d, disk cap) stays exactly as it is and keeps serving the live stream, recent search and flows. Hours that leave the local window are **archived** to the active destination instead of being deleted, and search can reach back into them on request.

What does not change: ingest, the pipeline, redaction before storage, the live stream, the local window's speed. Nothing reaches object storage that redaction would have removed; the archive is built from already-stored, already-sanitized lines.

## Model

```
ingest ─► pipeline ─► local SQLite (recent window, hourly partitions) ─► stream / search / flows
                              │ an hour leaves the window
                              ▼
                       archive job ─► segment (one hour) ─► active destination (Garage / R2 / S3 / S3-compatible)
                                                                │
search over an older range ◄── history reader (download, cache, attach) ◄──┘   also older destinations, read-only
```

- **Local window:** unchanged. `--retention` / Settings → Storage still sets it; the disk cap still wins locally.
- **Retained history:** everything older than the local window that was archived, across every connected destination, up to the history retention policy.
- **Destination:** a bucket (+ prefix) quiet writes to. One is **active** (new hours go there). Destinations that were active before stay connected **read-only** so their hours stay searchable ("Garage covers 09–21 Nov", newer hours in `production-r2`). Removing a destination is explicit.

## The segment: one archived hour

An archived hour is one object: **a SQLite file containing that hour's three tables** (`l_h` lines, `f_h` FTS5, `i_h` id index), the same layout the local store uses, plus a `segment` table with its metadata. Compressed with zstd.

Why SQLite and not NDJSON or Parquet:
- Search, id lookups and flow stitching run **the same SQL** over a downloaded segment as over a local hour (`ATTACH` read-only). No second query engine, no index to rebuild on read.
- The FTS and id index travel with the lines, so a one-id lookup in a 2-day range downloads 48 segments but never scans raw text.
- zstd on these files is ~5–10× (logs are repetitive); upload size, not row format, is what costs.
- Portability: anyone can open a segment with `sqlite3` after `zstd -d`. `quiet history export` (later) can write NDJSON from it.

Built with `VACUUM INTO` from a connection that sees only that hour's tables (copy into a temp db, vacuum, compress, checksum), off the writer thread.

**Object layout** (`<prefix>` defaults to `quiet/<instance id>/`; the instance id is a random id written to the catalog's `instance` table on first start, so two quiet servers can share a bucket):

```
<prefix>v1/hours/2026/11/22/482950.seg.zst      # hour number (unix ms / 3 600 000)
<prefix>v1/manifest/482950.json                 # lines, bytes (raw / compressed), sources, min/max ts, sha256, schema, created_at, redaction note
<prefix>v1/instance.json                        # instance id, name, first/last hour, written on connect
```

The manifest makes a bucket self-describing: a new server (or a disaster restore) can rebuild its catalog by listing `manifest/` (`quiet storage reindex`).

## Local catalog

New tables in `quiet.db` (not in a partition):

- `destinations (id, name, kind, endpoint, region, bucket, prefix, path_style, access_key_id, secret_enc, state, verified_at, active, capacity_bytes, at_capacity, created_at)`. `kind`: `garage` · `r2` · `s3` · `s3_compatible`. `state`: `ok` · `unavailable` (last error, next retry) · `read_only` · `removing`.
- `history_hours (hour, destination_id, key, lines, bytes_raw, bytes_stored, sources, min_ts, max_ts, sha256, archived_at)`: one row per archived hour; what search plans from, so it never lists a bucket.
- `history_gaps (hour, reason, at)`: hours that left the local window without being archived (`no_destination`, `destination_unavailable`, `disk_cap`, `excluded`), so search says "not retained" instead of silently returning nothing.

Secrets are encrypted at rest with a key in `<data dir>/secret.key` (created 0600 on first use) and never returned by the API (`preview: "AKIA••••7Q2X"`).

## Archiving

The retention job gains one step before it drops an hour:

1. An hour older than the local window, with an active, healthy destination → build its segment, upload, verify (`HEAD`: size + checksum metadata), write `history_hours`, then drop it locally. One hour at a time, oldest first; a failed hour is retried with backoff and never dropped before it is archived **unless the disk cap forces it** (then it is dropped and recorded in `history_gaps` as `disk_cap`).
2. No active destination → today's behaviour (drop) plus a `no_destination` gap row only if history was ever enabled.
3. Destination unavailable (DNS, 5xx, auth) → hours are held locally (`hold_window` already exists for export jobs), a system banner says "Retained history paused: <destination> unreachable · N hours waiting · retrying in 30s", and the disk cap is the only thing that can drop them.

**Backfill:** connecting the first destination offers to archive the hours still in the local window now (they would be archived anyway when they expire; backfill just means history has no hole if the window is shortened later). Switching the active destination offers **Copy history** from the old one (server-side copy where the providers allow, else download → upload), resumable, with progress; until it finishes both destinations stay searchable.

**Per-source rules:** a source with its own shorter window loses those lines locally before the hour archives, so they never reach history. A source can be **excluded from history** (Sources → a source → Settings, default included); its lines are left out of segments.

## Retention policy for history

Settings → Storage → Retained history:

- **Keep history for:** 7 · 30 (default) · 90 · 365 days · custom (days) · indefinitely. Applies to every destination, active or not (v1.1 storage boards).
- **Size limit per connector:** one shared limit; each connector's quiet data counts separately. Shortening it shows what will be deleted ("deletes 214 hours · 38 GB from production-r2 and garage-local") and needs confirming; deletion runs in the background.
- **At destination capacity** (optional capacity per destination; Garage reports it, R2/S3 have none unless set): **evict oldest** (delete the oldest hours to make room) or **stop archiving** (hold new hours locally, banner, gaps once the disk cap acts).
- **Cleanup blocked:** when a delete is refused (a key without delete permission, object lock), the hours stay listed as `cleanup_blocked` with the reason, and the banner says so. Nothing is retried in a tight loop.

## Destinations

- **Garage (default):** the compose files gain an optional `garage` service (single node, a volume, an admin token from env). On first start with `QUIET_GARAGE_*` set, quiet creates the bucket and key through Garage's admin API and connects it as `garage-local`. Without it, Garage is one of the choices in the Connect storage dialog.
- **Cloudflare R2, Amazon S3, S3-compatible** (MinIO, Backblaze B2, Wasabi, Ceph): endpoint, region, bucket, prefix, path-style, access key id + secret.
- **Verify** (on save, and a "Verify" button): put a small object, read it back, list the prefix, delete it. Each step is reported ("Write ✓ · Read ✓ · List ✓ · Delete ✗ AccessDenied: cleanup will be blocked"). A destination that can't write can't be made active.
- **Saved connectors:** several can be saved; one is active; switching asks whether to copy history.
- **Removing a connection:** "Keep its history in the bucket" (catalog rows go; reconnecting later and reindexing brings them back) or "Delete its history" (background delete, progress, cleanup-blocked if refused). The active destination can't be removed until another is active or history is turned off.

Client: the `object_store` crate (`aws` feature: S3, R2 and S3-compatible endpoints, path-style, retries, multipart) rather than the AWS SDK (much smaller, async, one API for every provider).

## Searching history

Search stays local-first. When the time range reaches past the local window:

1. The local part answers at once, as today.
2. The response says what history covers that range: per destination, the hours it holds, gaps, and what is expired (`before history retention`).
3. The UI offers **Search retained history** (or does it automatically for ranges under a small threshold, e.g. 6 hours). The server starts a **history job**: plans the hours (newest first, bounded: 168 hours per job), downloads segments into a local **history cache** (`<data dir>/history-cache`, LRU, `--history-cache 2GB`, separate from the disk cap), attaches each read-only and runs the same search SQL, streaming matches back.
4. Job states the screens draw: `retrieving` (n of m hours, MB), `done`, `cancelled` (user stopped it; partial results stay), `incomplete` (some hours failed or a destination was unavailable: listed per destination, "Garage not searched · 09–21 Nov"), and `expired` ranges ("No retained history before 09 Nov").
5. Results merge into the same list with a location tag (`local` · `garage-local` · `production-r2`) and the histogram greys out unsearched ranges.

**Flows:** stitching stays local and fast. When a flow's ids also appear in history ranges that weren't loaded (the id index of cached segments, or a cheap manifest check), the flow header says "Related history unavailable · Search retained history"; that runs a history job for the flow's ids and adds what it finds.

Exports over history ranges use the same job and the same sanitized data.

## API (sketch)

- `GET /api/storage/destinations` · `POST` (create + verify) · `PATCH /:id` · `POST /:id/verify` · `POST /:id/activate {copy_history}` · `DELETE /:id {delete_history}`
- `GET /api/storage/history` → policy, totals per destination, gaps, jobs (archive backlog, copy, cleanup)
- `PUT /api/settings/history {retention_days | null, at_capacity, enabled}` (owner)
- `POST /api/search/history {query}` → `{ job }` · `GET /api/search/history/:job` (progress + results page) · `DELETE` (cancel)
- `/api/system` issues: `history_unavailable`, `history_cleanup_blocked`, `history_at_capacity`

## Build order

- **5a · Store and connectors.** Instance id; `destinations` / `history_hours` / `history_gaps`; secret encryption; `object_store` client; verify; segment builder + uploader in the retention job (archive before drop, hold on failure, gaps); Garage compose service and bootstrap; Settings → Storage → Destinations screens (connect, verify, active, saved, remove). Tests with an in-memory object store and a local MinIO in CI-optional integration tests.
- **5b · Retention policy.** History retention (shorten with preview, custom, indefinite), capacity (evict / stop), cleanup blocked, backfill and copy history, removing a connection with or without its data, banners.
- **5c · Search across locations.** History cache, history jobs, merged results with location tags, coverage and gap reporting, cancelled / incomplete / expired states, histogram, Flow "related history unavailable", exports over history.

Each is its own PR with `make check` green.

## Changed by the v1.1 storage boards (23 November 2026)

- Activating a destination copies the hours still in the local window to it; the previous destination's history is not migrated and stays searchable while connected (v1.1-12, -13).
- The connection test runs list → write → read → delete and can run before anything is saved; Save follows a passing test (v1.1-05, -06).
- Amazon S3 can use the host's credentials, and pasted temporary credentials can carry a session token (v1.1-07, -25).
- History retention defaults to 30 days; one size limit per connector (v1.1-10).
- Removing a connector leaves its objects untouched; the UI no longer offers deleting them (v1.1-17). The API still can (`delete_history`).

## Decisions to confirm

1. **Segment format:** SQLite per hour (above) rather than NDJSON/Parquet.
2. **Local window unchanged**, archive-on-expiry; no "write-through" to object storage as lines arrive (history lags the local window by design; the local window is the durable copy until then).
3. **History is opt-in per instance** (off until a destination is connected), and per source it is on by default.
4. **`object_store`** as the client.
5. **Garage ships as an optional compose service**, not embedded in the quiet binary.
6. **One history retention for all destinations** in v0.1.1 (no per-destination or per-source history windows).
7. **Search of history is an explicit job** (with a small automatic threshold), not part of every search, so the default search stays as fast as today.
